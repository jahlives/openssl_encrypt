# Security Review — Findings

**Date:** 2026-06-10
**Branch:** `feature/v1.4.x-development`
**Commit:** `f8a00f82`
**Scope:** Full codebase (~93k LoC Python + Rust native ext, CI, packaging, systemd/D-Bus). Read-only review across core crypto, KDF/password/memory, PQC/asymmetric, keystore/HSM, CLI/IPC/sandbox, plugins, and supply chain. Top findings were verified directly against source.

> Status legend: `[ ]` open · `[~]` in progress · `[x]` fixed
> "Verified" = confirmed by reading the cited source during the review.

---

## Overall assessment

Modern paths are genuinely well-built: AEAD-by-default with metadata bound as AAD, per-file random salts/nonces from `secrets`, encrypt-then-MAC, `hmac.compare_digest` throughout, HKDF domain separation in the V7 asymmetric pipeline, a thoughtful streaming format (per-chunk nonces, chunk-index AAD, trailer HMAC), and a pure-Rust Threefish with zeroization and no `unsafe`.

Problems cluster in three areas: **legacy/"development" bypass code that still ships in production paths**, **a few false security claims**, and **the D-Bus + plugin attack surface**.

### [x] H3. Silent algorithm downgrade in PQCipher name resolution — FIXED (commit e1969035, 2026-06-10)
- **File:** `openssl_encrypt/modules/pqc.py:462-489`
- **Issue:** An unmatched algorithm name silently fell back to the first available KEM ("uses the enum value and hopes for the best").
- **Impact:** A caller requesting `ML-KEM-1024` (256-bit) could be served the weakest available level (demonstrated: a bogus name resolved to `Kyber512`) with only an optional stderr line.
- **Fix applied:** Both silent fallbacks (string-path `if not matched:` and enum-path "hope for the best") now `raise ValueError` listing the available algorithms. Legacy ML-KEM (Kyber*) names are preserved — the string path already normalizes/level-matches them, and the enum path now normalizes legacy values (`Kyber768` → `ML-KEM-768`) at the **same** security level before failing. Regression tests added (`test_unresolvable_algorithm_raises_no_silent_downgrade`, `test_legacy_names_still_resolve_to_same_level`). Full suite: 2091 passed, 14 skipped, 0 failed.

### [x] H4. Production keystore has no integrity protection — FIXED (commit de021bf5, 2026-06-11, branch feature/h4-keystore-integrity)
- **File:** `openssl_encrypt/modules/keystore_cli.py:266-297` (save), `186-264` (load)
- **Note:** This is the production class. The stronger `pqc_keystore.py` (whole-store AEAD + header-as-AAD) is **tests-only**.
- **Issue:** Whole store written as plaintext JSON; only per-key `private_key` fields are encrypted. `public_key`, `key_id`, `algorithm`, `defaults`, `dual_encryption` flags are cleartext and unauthenticated. The only password check (`test_key`) authenticates the password, not file contents.
- **Impact:** Anyone with write access to the keystore file can swap a stored public key for their own (undetectable on load); files later encrypted "to" that key ID go to the attacker. Can also flip defaults, delete entries, strip dual-encryption fields.
- **Fix applied (HMAC-over-canonical-JSON variant, per owner decision):** New keystore format v2 stores `integrity.{alg,mac}` = HMAC-SHA256 over the canonical JSON (sorted keys, fixed separators, MAC field excluded), keyed by a subkey derived from the master key with the domain-separation label `openssl_encrypt.keystore.integrity.v2`. `load_keystore` verifies the MAC **before trusting any field** and raises the new `KeystoreIntegrityError`; wrong password is disambiguated via the existing `test_key` and still raises `KeystorePasswordError`. Legacy v1 stores load with a loud warning and are auto-upgraded to v2 on load after password verification (skipped if the store has no `test_key`, to avoid sealing it under an unverified password; load still succeeds if the upgrade write fails). 18 regression tests in `test_keystore_integrity.py`. Full suite: 2111 passed, 14 skipped, 0 failed.
- **Accepted residual risk (1.4.x):** an attacker with write access can rewrite a v2 file as v1 (strip MAC + `version: 1`) and it loads with a warning — refusing v1 would break existing keystores on a stable branch; 1.5.x should consider rejecting v1 (or requiring an explicit opt-in flag). Tampering with `test_key` itself surfaces as a password error rather than an integrity error (fail-closed either way).

### [x] H5. Static, hardcoded USB master-key salt — FIXED (commit b2aeed02, 2026-06-10)
- **File:** `openssl_encrypt/modules/portable_media/usb_creator.py:330` and `:362` (verified)
- **Issue:** Every USB drive used `salt = b"openssl_encrypt_usb_v1.0_salt_2024"` (both multi-hash and PBKDF2-fallback paths). The comment claimed "deterministic but unique per USB" — false; it was global.
- **Impact:** A single precomputed dictionary cracked the master password for *any* drive ever made by this tool. Identical passwords across users yielded byte-identical keys.
- **Fix applied:** New drives generate a random 32-byte salt (`secrets.token_bytes`) stored in plaintext at `config/salt.bin` and read back at verify time; both derivation functions now take the salt explicitly. Pre-fix drives (no salt file) fall back to the retained `_LEGACY_FIXED_SALT` so they remain verifiable; new drives never use it. Regression tests added (unique salt + key per drive; legacy fallback; key separation). Full suite: 2093 passed, 14 skipped, 0 failed.

### [x] H6. Local GitHub OAuth token in the repo root — gitignore added (commit e02ca531, 2026-06-10)
- **File:** `.gh_token` (verified: 41-byte `gho_` token, mode `-rw-r--r--`)
- **Re-verified scope (2026-06-10):** **never tracked, never committed on any branch/ref, value never appears anywhere in history, not staged** (`git ls-files`, `git log --all`, pickaxe `-S`, `git diff --cached` all clean). So there is **no git leak** and rotation is NOT required on that basis — the only exposure was (a) world-readable on the local box and (b) no ignore rule, making a future `git add .` a latent footgun.
- **Fix applied:** Added `.gitignore` rules for `.gh_token`, `*.token`, `.env`, `.env.*`, plus `output.txt`/`precommit_output.txt`; `.coverage*` was already ignored. Verified all three previously-untracked files are now ignored.
- **Left to user judgment:** rotating the token and/or `chmod 600` — only warranted if this sandbox environment itself is considered untrusted, not because of any git exposure.

### [x] H7. D-Bus: any-user policy + root service, no per-caller authorization — FIXED (commit d0dc0bab, 2026-06-12, branch feature/h7-dbus-authz; includes L8)
- **Files:** `openssl_encrypt/dbus/ch.rmrf.openssl_encrypt.conf` (verified: `<policy context="default">` allows anyone to call the `Crypto` interface); `systemd/openssl-encrypt-dbus.service` (verified: no `User=`, runs as root); handlers in `openssl_encrypt/modules/dbus_service.py`.
- **Issue:** Service exposes `EncryptFile`, `DecryptFile`, and destructive `SecureShredFile` with zero caller authorization (no Polkit, no UID inspection).
- **Mitigating reality:** `run_service()` actually binds `dbus.SessionBus()` (`dbus_service.py:1082`, verified), so *as literally shipped* it is session-scoped, not the root system-bus daemon the `.conf`/unit describe. But the shipped policy + unit describe the dangerous configuration, and an admin aligning the daemon to the unit (SystemBus) gets full cross-user shred/decrypt with no credential. Even on the session bus there is no per-caller authz.
- **Design clarification (owner, 2026-06-12):** the system-bus deployment is intentional — it exists so a NON-ROOT ADMIN can encrypt/decrypt files only root has access to. The fix therefore implements the missing authorization instead of removing the deployment.
- **Fix applied:** All state-touching methods now resolve the caller (`sender_keyword`) and consult `_authorize_caller()` before anything else, fail-closed (missing sender / unresolvable UID / polkit unreachable → deny, audit-logged). Session bus (default): caller UID must equal service UID. System bus (new explicit `--system` flag): polkit `CheckAuthorization` per method using the shipped action ids (encrypt/decrypt/keystore/generate_key; shred and delete_key for destructive ops) with `AllowUserInteraction`. The polkit `.policy` was tightened (`allow_active` yes → `auth_admin_keep` for encrypt/decrypt/keystore/generate_key; shred/delete_key already `auth_admin`). Path policy is mode-dependent: system mode reaches the filesystem minus blocked critical paths (`/etc/shadow`, `/boot`, `/proc`…, with `/root` unblocked — that's the point), session stays home/tmp. New hardened system unit + system-bus activation file (`User=root`); user unit got the L8 hardening set (so **L8 is closed by this commit too**). 25 regression tests (`test_dbus_authz.py`, mocked dbus). Full suite: 2228 passed, 0 failed.
- **Residual / follow-ups:** polkit integration is unit-tested against mocks, not a live polkitd — needs one manual smoke test on a real system-bus install (documented in the port guide). L12 (passwords cross the bus as plain `str`) remains open and is more relevant now that the system path is real.

### [x] H8. Plugin sandbox bypassable and not enforced on the default path — FIXED (commit c2a7dd6e, 2026-06-12, branch feature/h8-plugin-sandbox)
- **Files:** `openssl_encrypt/modules/plugin_system/plugin_sandbox.py`, `plugin_ast_analyzer.py`, `plugin_manager.py:163-232`
- **Issues:**
  1. File-access restriction (`_restrict_file_operations`) is installed only in **threading** mode, but the default is **process isolation** (`_plugin_worker`), which never patches `open()`. A plugin declaring no file capabilities can still read `~/.ssh/id_rsa` / write arbitrary files. (Path-traversal unit tests only exercise `use_process_isolation=False` — the non-default mode.)
  2. AST denylist misses `__traceback__` → `tb_frame.f_back.f_globals`, recovering real builtins and reaching `eval` via a `Subscript`-call the analyzer doesn't flag.
  3. Plugin module top-level code runs unsandboxed at `exec_module` import time; the only gate is the denylist scanner.
- **Fix applied:** (1) `_plugin_worker` now runs the full `_setup_restricted_environment()` (file/network/process patches + import guard, capability-honouring) after AST validation and before `plugin.execute()`, so the default process-isolation path is sandboxed identically to threading mode. (2) Frame/traceback attrs (`__traceback__`, `tb_frame`, `tb_next`, `f_back`, `f_globals`, `f_locals`, `f_builtins`, `gi_frame`, `cr_frame`, `ag_frame`) added to `DANGEROUS_DUNDER_ATTRIBUTES` (consulted by both `visit_Attribute` and the `getattr()` check). (3) `_validate_plugin_file` refuses plugins whose file or containing directory is group/world-writable (sticky dirs like `/tmp` exempted), checked before the built-in trust shortcut — closing the drop-in/rewrite window for import-time code. 15 regression tests (`test_plugin_sandbox_h8.py`). Full suite: 2243 passed, 0 failed.
- **Also hardened (required for correctness):** `_plugin_worker` is written for a spawned subprocess but mutates process-wide state (resource limits, cwd, monkeypatched builtins, temp dir); it now restores all of it in `finally`. Resource limits lower only the **soft** limit (preserving the original hard limit) because lowering the hard `RLIMIT_CPU` is irreversible for an unprivileged process — the prior `(60,60)` was unrestorable and, when the worker runs in-process, leaked a 60 s cumulative-CPU cap. See [[plugin-worker-process-state]].
- **Residual / follow-ups:** issue 3's deeper form (module top-level code still executes under exec_module with only AST + the new permission gate — not a fully restricted `__builtins__` runtime) is mitigated, not fully sandboxed; a restricted-import runtime at load time is a larger 1.5 item. Dynamic `getattr(obj, <computed>)` remains severity "high" (warn, not block) to avoid breaking legitimate plugins.

## Medium

### [~] M2. Untrusted KDF parameters processed before authentication (DoS) — MITIGATED BY DESIGN (owner decision 2026-06-12)
- **File:** `openssl_encrypt/modules/crypt_core.py:8796-8826` then `:9302-9359`
- **Issue:** Metadata `hash_config`/`kdf_config` (Argon2 `memory_cost`, iterations) fed into `generate_key` before any AEAD authentication. A tampered file declaring multi-GB Argon2 memory forces that allocation before the tag fails.
- **Owner disposition (accepted, not fixing with a hard cap):** Two existing controls cover the threat for the intended (expert) usage:
  1. **Interactive decrypt warning + abort window** — `decrypt_file` prints a DECRYPTION COST ESTIMATE (per-op time/peak memory, with threshold warnings) and waits 2 s for Ctrl+C before doing the KDF work (`crypt_core.py:9002-9042`). A human sees "Peak Memory ~32 GB" and aborts.
  2. **Opt-in remote metadata-hash plugin** — when enabled, the metadata hash is stored remotely and tampering is reliably detected *before* any KDF/hash processing, fully closing the DoS for those users.
  A hard upper bound is deliberately NOT added because it would also cap legitimate expert configurations.
- **Verified residual (2026-06-12):** the warning+2 s gate is `if not quiet and not no_estimate` (`crypt_core.py:9003`), so it is **skipped on every non-interactive path**: `decrypt_file(..., quiet=True)`, batch/scripted CLI use, and notably the **D-Bus service** (`dbus_service.py:766-775` calls `decrypt_file(quiet=True)`). On those paths, for users who have NOT enabled the remote-hash plugin, a tampered file with insane Argon2 `memory_cost` still triggers the allocation before the tag fails — and the D-Bus system service may run as root. No hard cap exists in code (verified: no max/clamp on `memory_cost` before KDF). **Accepted as-is** per owner; if revisited, the minimal fix is a cap applied only on the quiet/non-interactive decrypt paths (or in `dbus_service.py`), not a global floor.

### [x] M3. Balloon defaults give ~512 bytes of "memory hardness" — FIXED (commit on branch feature/m3-balloon-defaults, 2026-06-12)
- **Files:** `crypt_core.py:2371-2373`; `parallel_kdf.py:289-291`; `balloon.py:245-248,313-316,64`
- **Issue:** `space_cost=16` × 32-byte SHA-256 block ≈ 512 B buffer (~3000 hashes) in the independent-XOR path — GPU-trivial. `max_space_cost = 1_000_000` also caps Balloon at ~32 MB. If a user enables only `balloon` in the XOR composition, stretching is effectively absent.
- **Confirmed live (empirically):** a `format_version=11` balloon-only encryption stored `balloon: {"enabled": true}` (space_cost **not persisted**) and completed in **0.03 s** — i.e. the 512-byte default was actually used. (The non-XOR v10 path already defaulted to 65536 / 2 MiB and persisted it; M3 was specifically the v11 independent-XOR + `parallel_kdf` paths.)
- **Owner decision (2026-06-12):** this is a *silent* weak default (the user can't see they're getting 512 B), distinct from M4 which was the user's *explicit* choice — so unlike M4 it must be fixed. New default 2 MiB (`space_cost=65536`); explicit sub-floor values are warned about (with the byte cost) but respected.
- **Fix applied:** new encrypt-time helper `_apply_balloon_security_defaults(hash_config)` (called once in `encrypt_file`, encrypt-path only) sets a memory-hard default `space_cost=65536` (and pins `time_cost=3` for the defaulted case so the cost is ~1 s rather than ~9 s under the v11 `time_cost=20` read-default) and **persists it into metadata**; an explicit `space_cost` below the 512 KiB floor (`space_cost < 16384`) prints a loud warning showing the byte cost but is respected (M4-consistent). Handles both the top-level and nested (`derivation_config.kdf_config`) balloon config shapes.
- **Backward compatibility (critical, verified):** the decrypt-side read-default (`crypt_core.py:2371` / `parallel_kdf`) was deliberately **left at 16**. Old v11 files stored only `{"enabled": true}` and re-derive with that default; changing it would have made them undecryptable. The fix lives only in the encrypt path and persists the value, so new files carry their own `space_cost` and old files still decrypt — proven by a regression test that decrypts a simulated pre-fix weak file.
- **Not changed:** `max_space_cost = 1_000_000` (~32 MB) left as-is — the pure-Python Balloon makes ≥64 MiB (~35 s) impractical (2 MiB ≈ 1 s, 8 MiB ≈ 4.4 s), so a higher ceiling would only enable unusably-slow configs.
- **Tests:** `test_balloon_defaults_m3.py` (10): default-fill (top-level + nested), explicit-low warned-but-respected, safe value not warned, disabled untouched, quiet suppresses warning, new v11 file strong+persisted+round-trips, and the legacy-weak-file-still-decrypts backward-compat test. Full suite: 2281 passed, 0 failed.

### [~] M4. No minimum-strength enforcement on KDF parameters — DISMISSED (by design, owner decision 2026-06-12)
- **Files:** `registry/kdf_registry.py:221-234,461,476-477,575-580`; `parallel_kdf.py:234-262`; `crypt_core.py:2371-2373,3488-3490`
- **Issue (as originally filed):** `iterations=1`, Argon2 `time_cost=1, memory_cost=8`, scrypt `N=2` are accepted without warning. All params come via `kdf_config.get(key, default)`, so a misspelled/tampered key silently falls back. Registry PBKDF2 default (100k) also conflicts with the 600k used in `crypto_secure_memory.py:353`.
- **Re-analysis (2026-06-12):** the "tamper metadata to weaken KDF → cheaper offline brute force" angle is **not a real attack**: the derived key is `KDF(password, salt, params)`, so lowering `params` on an existing file just yields a different key and the AEAD tag fails — the attacker gains no oracle and must use the *original* (strong) params to attack the real ciphertext. So M4 is purely an encrypt-time weak-config / weak-default concern, not an attacker mitigation.
- **Owner disposition:** **Dismissed by design.** This tool targets expert users who know what they are doing; if such a user asks for 1 iteration, they get 1 iteration. A hard floor would fight that intent. No floor will be added.
- **Note (separate, minor, not part of M4 security):** the registry PBKDF2 default of 100k vs 600k elsewhere is an internal consistency nit; fix opportunistically if those paths are touched, but it is not a vulnerability.

### [ ] M5. Raw `SHA-256(shared_secret)` used as symmetric key (no KDF / no domain separation)
- **File:** `openssl_encrypt/modules/pqc.py:653` (encrypt), `:908` (decrypt)
- **Issue:** KEM shared secret fed through a bare hash — no salt, no `info`, no algorithm binding. Inconsistent with `asymmetric_core.PasswordWrapper` (HKDF-SHA256 with `info=b"openssl_encrypt.password_wrap.v2"`). FIPS 203 recommends a KDF step for hybrids.

### [~] M6. Master-key private-key encryption uses no AAD — LARGELY MITIGATED BY H4 (verified 2026-06-12, commit on branch feature/m6-verify-h4-mitigation)
- **File:** `openssl_encrypt/modules/keystore_cli.py:1248-1305` (`_encrypt_data_with_key`/`_decrypt_data_with_key`)
- **Issue:** `aes.encrypt(nonce, data, None)` — ciphertexts not bound to `key_id`/`algorithm`/`public_key`. Blobs can be moved between entries. The dual-encryption path in the same file does it correctly (`aad = f"keystore:{key_id}:dual"`).
- **Re-analysis after H4 (verified):** the H4 whole-store integrity MAC (`_compute_integrity_mac`) is computed over the canonical JSON of `{k:v for k,v in keystore_data.items() if k != "integrity"}`, which **includes every entry's `private_key` field**. Moving an encrypted blob from one entry into another changes the canonical JSON, so the stored HMAC no longer matches and `load_keystore` raises `KeystoreIntegrityError` before any field is trusted. An attacker with write access but **without the master password** (the M6 threat model — they cannot recompute the MAC) is therefore blocked. An attacker **with** the master password can re-MAC, but with the master password they can already decrypt/re-encrypt any entry, so per-entry AAD would not help. Proven by `test_keystore_integrity.py::test_private_key_blob_move_between_entries_rejected` (moves only the `private_key` blob → rejected).
- **Disposition:** downgraded — no separate per-entry AAD fix needed on 1.4.x. **Optional 1.5 defense-in-depth:** add `aad = key_id` (or `algorithm` + hash(public_key)) to the master-key wrap anyway, so the binding holds even independent of the store MAC and a future format could tolerate partial loads. Tracked but not required.

### [x] M7. 10k-iteration PBKDF2 hash of the file password stored in metadata — FIXED (commit 6204bff3, 2026-06-12, branch feature/m7-drop-pbkdf2-verifier)
- **File:** `openssl_encrypt/modules/keystore_wrapper.py:90-104` (write), `:670-686` (verify)
- **Issue:** A PBKDF2-HMAC-SHA256 hash of the file password at only 10,000 iterations is stored in cleartext file metadata as a UX pre-check — independent of the strong Argon2id derivation. Gives a cheap offline brute-force oracle for a real secret (the dual-encryption second factor).
- **Fix applied:** The verifier is no longer written — it was redundant, since the dual-encryption AES-GCM tag already authenticates the file password during key retrieval (`keystore_cli` `get_key`). `encrypt_file_with_keystore` stops deriving/storing `pqc_dual_encrypt_verify[_salt]`; `decrypt_file_with_keystore` still honours the field on legacy files (backward compat) and otherwise relies on the AEAD tag (no more "verification skipped" warning). Wrong passwords are still rejected (by the tag). Regression test `test_pqc_dual_encryption_no_pbkdf2_verifier_in_metadata` asserts absence + round-trip + wrong-password rejection. Full suite: 2244 passed, 0 failed.
- **Residual:** files written before this change still carry the weak hash in their metadata permanently; only new files are clean. This is a standalone `hashlib.pbkdf2_hmac` use (not the KDF-registry PBKDF2) — flagged in the 1.5 porting guide so the planned full PBKDF2 removal catches it.

### [x] M8. Identity import is TOFU with no key-change detection — FIXED (commit on branch feature/m8-identity-tofu, 2026-06-12)
- **File:** `openssl_encrypt/modules/identity.py`, `identity_cli.py`, `crypt_cli_subparser.py`
- **Issue:** `verify_fingerprint()` recomputes from the same keys in the import, so it only detects in-bundle corruption — no authenticity protection. `add_identity(overwrite=...)` silently replaces a contact's keys on re-import. Partial-prefix fingerprint matching (`startswith`) can resolve to the wrong identity (`""` matches the first).
- **Fix applied (3 parts):**
  1. **TOFU key-change detection (core).** `add_identity` now compares the incoming fingerprint to the stored one (via `get_by_name`) and raises the new `IdentityKeyChangedError` (carrying old+new fingerprints) when they differ — **even with `overwrite=True`**. Replacing a pinned key requires the explicit new `allow_key_change=True`. CLI: `cmd_import` catches it, prints old vs new fingerprint, and per owner decision **refuses non-interactively** (exit 1, instructs `--allow-key-change`) but **prompts on a TTY** to accept. New `--allow-key-change` flag for scripted acceptance. `cmd_create` passes `allow_key_change=True` (own-identity regen/key-rotation is a deliberate local action, not the contact-substitution threat; the keyserver `KeyResolver` path refuses by default).
  2. **Safe fingerprint lookup.** `get_by_fingerprint` no longer uses `startswith` — it requires the **full** fingerprint (owner decision; verified the real callers, `crypt_cli.py` sender resolution, pass `metadata[...]["sender"]["key_id"]` which is the full `sender.fingerprint`), raises `IdentityError` on empty input, and raises the new `IdentityAmbiguousError` on a multi-match. Kills the `""`-matches-first footgun.
  3. **Honest naming.** `verify_fingerprint()` → `check_fingerprint_consistency()` (docstring states it proves internal consistency, NOT authenticity); `verify_fingerprint` kept as a deprecated alias.
- **Out of scope (flagged, not silently skipped):** real first-contact *authenticity* (verifying a contact's bundle is signed by a trusted party / web-of-trust) is a larger PKI feature; M8 is specifically pinning + change detection.
- **Tests:** `test_identity_tofu_m8.py` (12): same-key re-import allowed, changed-key refused even with overwrite (+ pinned key unchanged), accepted with `allow_key_change`, new name unaffected; empty/partial/nonexistent/ambiguous fingerprint lookups; `check_fingerprint_consistency` + alias + tamper-detection. Existing 93 identity tests still pass. Full suite: 2293 passed, 0 failed.

### [~] M9. Debug mode logs derived keys, plaintext, and KDF intermediates in hex — DISMISSED (by design, owner decision 2026-06-12; same disposition as CC-2)
- **Files:** `crypt_core.py` (pervasive: 6677, 6711-6713, 6820, 9625, 9672, 9780, 10046, 3461, 3469, 3528, 3545); `parallel_kdf.py:710,719`
- **Issue (as filed):** With `--debug`, raw keys, full plaintext, nonces, and Balloon/Argon2 intermediates (whose XOR reconstructs the combined key) go through standard `logging`. Any file/syslog/journald handler persists secrets. Contradicts CLAUDE.md "never log/print keys."
- **Owner disposition:** **Dismissed by design.** Debug logging is a deliberate, necessary capability for diagnosing otherwise-intractable crypto issues. It is off by default and requires the explicit `--debug` flag, which prints a prominent, comprehensive warning before any sensitive output (`crypt_cli.py:4630-4643`): it states "SENSITIVE DATA LOGGING ACTIVE", enumerates that it logs "Password hex dumps during key derivation", and instructs "❌ DO NOT use --debug with production data or real passwords / ✅ Only use for testing with dummy/test data / ⚠️ Debug logs may be stored in log files or terminal history". The warning already discloses the exact persistence concern the finding raised. Same rationale as the already-dismissed **CC-2**.
- **Note:** the CLAUDE.md "never log/print keys" guidance is treated as applying to normal operation; the explicit, warned `--debug` path is the sanctioned exception for an expert tool. No change.

### [x] M10. Password-wipe code is dead / ineffective — FIXED (b: commit fd160b73; a: commit on branch feature/m10a-kdf-wipe, 2026-06-12)
- **Files:** `registry/kdf_registry.py` (all backends); `secure_memory.py:147-336`
- **Issue:** (a) `password_bytes != password` guard is always False (`bytes` and `bytearray`/`SecureBytes` are value-equal in Python) → the wipe never runs, and it targets `bytearray(password_bytes)` (a throwaway copy) anyway. (b) `secure_memzero` operates on `bytearray(data)` (a copy) for immutable `bytes`/`str`, never wiping the original, while returning `True` ("verified zeroed"). Affects callers passing `bytes`.
- **Part (b) FIXED:** `secure_memzero` now returns `False` (or raises in `strict=True` mode) for immutable `bytes`/`str` and un-writable memoryview input instead of falsely reporting success; mutable buffers (bytearray/SecureBytes/writable memoryview) are still wiped in place and return `True`. A best-effort wipe of the transient copy is still performed. ### [ ] I-XChaCha. "XChaCha20-Poly1305" uses only 12 of its 24 nonce bytes (labeling / dead-code, no security impact)
- **DECISION (2026-06-10):** Deferred to **release 1.5** — implement real 192-bit XChaCha20 then. **1.4.x is left as-is** (no security defect on this branch; per-file unique keys mean the effective 96-bit nonce is never reused). Do NOT change the 1.4.x XChaCha nonce handling.
- **Severity:** Info/Low (was originally filed as Medium M1; downgraded after re-verification and reviewer pushback — see note below).
- **Files (verified):**
  - Class `XChaCha20Poly1305._process_nonce` — `crypt_core.py:279-358`. This layer is **correct**: for a 24-byte input it derives the 12-byte library nonce from *all 24 bytes* via `HKDF(SHA256, salt=nonce[:16], info=nonce[16:])` keyed by `self.key` (lines 314-332).
  - Encrypt call site — `crypt_core.py:6941-6943`: `cipher.encrypt(nonce[:nonce_size], data, aad)` with `nonce_size = 12`.
  - Decrypt call site — `crypt_core.py:10014-10022`: `cipher.decrypt(nonce[:effective_size], ...)` with `effective_size = 12`.
  - Sizing tables: `get_algorithm_nonce` (`6627-6639`) returns `nonce = token_bytes(24), 12` in production; decrypt sizing (`9393-9400`) returns `[(24, 12)]` (stored 24, effective 12).
- **What actually happens:** The call sites slice the 24-byte nonce to `nonce[:12]` **before** handing it to the class, so `_process_nonce` always hits the `elif len(nonce) == 12:` passthrough (lines 333-335). The 24-byte HKDF branch is **dead code in the real pipeline**. The remaining 12 nonce bytes are stored in the file header but never influence the keystream. The inline comment confirms it: *"Even with 24-byte stored nonce, we use 12 bytes for actual encryption with the library."*
- **Why this is NOT a vulnerability:** Keys are unique per file (per-file random salt → unique derived key). XChaCha's 192-bit nonce only buys misuse-resistance under a *reused* key; there is no key reuse here, so reducing the effective nonce to 96 bits creates no collision risk. Security is identical to plain ChaCha20-Poly1305, which is sound in this construction. (This is the basis on which earlier reviews dismissed it — though those reviews appear to have validated the *class* and not the *call sites*, which is the trap.)
- **Residual issues (cosmetic/correctness):** (1) the `XCHACHA20_POLY1305` name and docstrings advertise extended-nonce robustness the pipeline doesn't apply; (2) 12 bytes per file are stored for nothing.

#### Remediation analysis — what "using the full 192 bits" would actually require, and what breaks

**Critical caveat: the obvious one-line fix gains nothing.** Simply passing the full `nonce` (dropping `[:nonce_size]`) so the existing HKDF branch in `_process_nonce` runs does **NOT** deliver 192-bit security. That branch (`crypt_core.py:323-332`) funnels all 24 bytes into a **96-bit** output under the **same key**: `HKDF(SHA256, length=12, salt=nonce[:16], info=nonce[16:]).derive(self.key)`. The keystream is still `ChaCha20(key, 96-bit value)`, so collisions remain birthday-bounded at **2⁴⁸** — identical to a 96-bit random nonce. You would pay a backward-incompatible format change to move from "96-bit random nonce" to "96-bit PRF-of-192-bit nonce" with **no real gain in nonce-misuse resistance**. (This is likely the deepest reason the finding keeps getting dismissed: reviewers who notice the slice assume the HKDF "fixes" it — it does not.)

**What real XChaCha20 needs:** genuine HChaCha20 subkey derivation — run `nonce[:16]` through HChaCha20 to derive a fresh 256-bit subkey, then `ChaCha20-Poly1305(subkey)` with a 96-bit nonce of `b"\x00\x00\x00\x00" + nonce[16:24]`. Collisions then require the full 24-byte nonce to repeat (2⁹⁶) or a subkey collision (2¹²⁸). Two routes:
- **Route A — libsodium/PyNaCl (recommended):** `nacl.bindings.crypto_aead_xchacha20poly1305_ietf_{encrypt,decrypt}`. Audited, real XChaCha20-Poly1305-IETF with a 24-byte nonce. **Verified: PyNaCl is NOT installed and NOT a declared dependency, and `cryptography` 46.0.6 does not expose XChaCha (`from ...aead import XChaCha20Poly1305` fails).** So this means adding a new native dependency (touches `requirements*.txt`, `pyproject.toml`, Docker/Flatpak manifests, portable-USB/mobile builds — intersects the unpinned-native-dep findings already in this report).
- **Route B — hand-rolled HChaCha20** on `cryptography`'s raw `ChaCha20` primitive. No new dependency, but it is custom crypto (flagged by CLAUDE.md) and **must** ship with RFC/libsodium known-answer test vectors or it is worse than the status quo.

**Code touch-points (small, localized):** `get_algorithm_nonce` (`6627-6639`) → return `(token_bytes(24), 24)` in production; encrypt site `6943` and decrypt site `10020` → pass full `nonce`; decrypt sizing table (`9393-9400`) → add `(24, 24)` candidate; `_process_nonce` (`314-332`) → replace HKDF with the real construction (or bypass the wrapper for libsodium); `streaming.py:100, 205-209, 280-283` → bump width / adjust `derive_chunk_nonce`.

**What could break:**
1. **Backward compatibility (dominant risk).** Every existing XChaCha file was written as `ChaCha20(key, nonce[:12])`; a real construction changes the keystream, so old files won't decrypt on the new path. **The one-shot format already stores 24 bytes today** (`return nonce + encrypted_payload`), and the new format would too — so **old and new files are indistinguishable by nonce length** (both `(24, …)`). Disambiguation requires either bumping `format_version` / minting a distinct algorithm id (`xchacha20-poly1305-v2`), **or** trial decryption (try real-XChaCha, fall back to legacy 12-byte passthrough on `InvalidTag`). The AEAD tag makes trial decryption safe and the codebase already does multi-candidate decrypt, but it costs two AEAD attempts per legacy file and the legacy path must be kept indefinitely.
2. **AAD binding.** Metadata is bound as AAD. Bumping `format_version`/algorithm id changes new-file AAD (fine), but the legacy decrypt path must reproduce the *old* AAD exactly. Trial decryption handles this naturally; a hard cutover does not.
3. **Streaming gains nothing.** Per-chunk nonces are already made unique by `derive_chunk_nonce(prefix, chunk_index)` and never repeat under a key by construction, so XChaCha misuse-resistance buys nothing there — 24-byte chunk nonces are pure bloat and still deterministic HKDF output, not random 192-bit nonces. Prefer leaving streaming at 12 and only changing one-shot (wrapper must then cleanly support both widths).
4. **`test_mode` path.** `get_algorithm_nonce(..., test_mode=True)` forces 12-byte nonces "for compatibility with existing tests" (wired via `is_test_env` at `6877`). Fixed-nonce/KAT XChaCha tests and `generate_testfiles*` fixtures need regenerating.
5. **Custom-crypto risk (Route B).** A subtle HChaCha20 constant/counter-layout error silently yields a non-standard, non-interoperable cipher that still round-trips — the worst kind of bug. KATs mandatory.

**Recommendation:** Since there is **no actual security defect today** (per-file unique keys mean the 96-bit nonce is never reused) and a real fix is a backward-incompatible format change plus either a native dependency or hand-rolled crypto, the cost/benefit favors the **honest rename**: label it `chacha20-poly1305` (it already is one), stop storing the 12 dead bytes for *new* files, and keep reading old `xchacha` files via the existing passthrough. Only pursue true 192-bit XChaCha if a concrete requirement for nonce-misuse resistance under *key reuse* emerges (this design has none). If pursued, **Route A (libsodium) gated behind a new `format_version` with trial-decrypt fallback** is the safe shape and is TDD-able starting from libsodium KAT vectors.

## Notable strengths (verified — preserve these)

- All salts/nonces/keys use `secrets`/`os.urandom`; no `random` module in any key/IV/salt path. Fresh salt + fresh key per file.
- AEAD-by-default with metadata bound as AAD defeats algorithm-confusion/downgrade and metadata tampering for AEAD files.
- Encrypt-then-MAC for Camellia with HKDF-SHA256 HMAC key separation; constant-time verification.
- `hmac.compare_digest` centralized for all integrity hashes/tags/MACs; no `==` on digests.
- Streaming format: per-chunk HKDF nonces, chunk index + count bound into per-chunk AAD (anti-reorder/truncation), trailer HMAC, `ciphertext_len` bound against memory exhaustion, output deletion on auth failure.
- V7 asymmetric pipeline: verify-before-KDF DoS protection (fails closed), HKDF with domain separation, Argon2id at-rest private keys + AES-256-GCM with AAD identity/purpose binding, path-traversal-safe identity names.
- Cipher/signature registries are `freeze()`-d; no null/plaintext cipher; FIPS 203/204/205 naming.
- Diceware uses `secrets.SystemRandom` exclusively, validates wordlists, computes correct entropy.
- Production keystore uses atomic mode-at-creation writes (`create_secure_file` `O_CREAT`+umask then `os.replace`); key bundles recompute fingerprints and verify ML-DSA self-signatures; safe trust defaults (interactive trust default-No).
- Telemetry is opt-in, minimized (no filenames/paths/keys), TLS enforced. Keyserver verifies bundle signatures before caching, HTTPS-only, optional cert pinning.
- No `shell=True`/`os.system`/`eval`/`exec`/`pickle`/`yaml.load` of user input in reviewed surface. GUI invokes CLI via argv list, password via env.
- Threefish native ext is pure Rust, zero `unsafe`, `ZeroizeOnDrop` on keys, `Cargo.lock` committed.
