1.4.10 NOT RELEASED FEATURE
Unreleased (in development)
NOT YET RELEASED. GUI capability manifest (gitlab#265, github#140): a new crypt capabilities command prints a machine-readable JSON description of what this build of the tool supports — schema_version, cli_version, line, commands, flags, features, command_flags, json_endpoints and json_fields — so a single desktop app, released on its own schedule, can gate its screens and options on whichever version of the command-line tool it is paired with, instead of a hardcoded version→feature matrix. The commands come from the tool's authoritative command list and the flags are introspected from the live argument parsers (including each per-command subparser), so the description cannot drift from what the tool actually accepts; features are computed from that surface, so a feature reports false automatically when the command or option it needs is absent (for example steganography on a line that dropped it). Options hidden from --help are excluded, so the list never claims more than the visible surface. The description carries only public command and option names — never a secret value — and does not depend on your environment. This is the foundation for shipping the desktop app as a separate application from the command-line tool. Two-app Flatpak split (gitlab#267, github#142): this Flatpak is now the command-line tool only — the desktop GUI is its own Flatpak app, OpenSSL Encrypt GUI (com.opensslencrypt.OpenSSLEncryptGui). Existing installs of this ID upgrade in place to the CLI-only app; if you used the combined package for its GUI, install the GUI app once under its new ID. The CLI app also drops the desktop-only sandbox permissions (display, GPU, accessibility), reducing its footprint. Uniform JSON output (Phase 1a, gitlab#268): version, show-version-file, list-algorithms, check-argon2 and check-pqc gain --json, each printing a single structured document on stdout for scripts and the desktop app; the capabilities manifest lists the JSON-capable commands. Phase 1b: info, analyze-config, template list, list-plugins, plugin-info and security-info are JSON-capable too; requesting JSON from a command that cannot produce it is refused instead of silently ignored. Phase 1c: the verification commands (verify-integrity, verify-signature, verify-usb) are JSON-capable. Phase 2: the file operations and password commands report machine-readable results as well.
1.4.9 STABLE RELEASE SECURITY FEATURE
2026-08-12
Security hardening: Derive-password memory hygiene (2026-07-13): the derive-password command now zeroizes the hardware pepper and the derived-key output buffer after use instead of leaving them in process memory (derived outputs unchanged). Legacy seed zeroization (2026-07-13): key derivation for legacy sequential formats now builds its password+salt+pepper seed in a wipeable buffer that is zeroized after use (derived keys are byte-identical). Balloon v14 fail-closed (2026-07-13): version-14 files whose balloon KDF metadata is missing the space_cost field are refused with a clear error instead of silently deriving with a weak fallback; older files (where the fallback is required for compatibility) are unaffected. KDF cost memory ceiling (2026-07-24, gitlab#128): decryption now refuses a crafted file or keystore whose key-derivation cost parameters (Argon2 memory, scrypt N, balloon space_cost) would exhaust memory — previously an attacker-supplied file could drive a multi-terabyte allocation and OOM-crash the host on decrypt before any password check. Peak memory is estimated before key derivation runs and refused above an 8 GiB safety ceiling (four times the largest built-in preset, so no legitimate file is affected), overridable per file with --allow-high-kdf-cost or an interactive confirmation. Only memory is hard-guarded; CPU/time cost stays advisory. Identity-file KDF cost bound (2026-07-24, gitlab#129): identity unlock now clamps the Argon2 cost parameters read from an identity file to sane maxima before deriving the key — a tampered or attacker-authored identity with a gigabyte-scale memory_cost could otherwise OOM the host on unlock before authentication. Legitimate identities use the 64 MB default and are unaffected. Plugin signature enforce-by-default (2026-07-24, gitlab#130): the plugin loader now refuses an unsigned or unverifiable third-party plugin by default instead of running it behind a bypassable code scan — loading arbitrary plugin code was effectively arbitrary code execution for anyone who could place a file in a plugin directory. A non-built-in plugin must now carry a valid signature from an enrolled trust anchor, or it is refused before its code runs; built-in bundled plugins are unaffected, so no shipped functionality changes. Users who intentionally load unsigned third-party plugins can opt back in via the OPENSSL_ENCRYPT_PLUGIN_SIGNATURE_POLICY=warn (or off) environment variable. The built-in trust shortcut is now scoped to the shipped plugin subtree, so the third-party plugin directories (user/community/official) are no longer auto-trusted and must carry a valid signature. PQC keyfile Argon2id wrap (2026-07-24, gitlab#131): a .pqc keyfile created with --pqc-keyfile wrapped the long-lived post-quantum private key with a weak PBKDF2-SHA256 100k key, so an attacker who obtained the keyfile could brute-force the wrapping password cheaply offline. New keyfiles now wrap the private key with Argon2id (consistent with the rest of the tool); existing keyfiles still decrypt unchanged. Re-save or regenerate a keyfile to move it onto the stronger wrapping. Dual-encryption verifier (2026-07-24, gitlab#131): dual-encrypted files stored a weak 10k-PBKDF2 file-password verifier in cleartext metadata that an attacker with the file could brute-force offline. It is no longer used or written; the file password is authenticated by the keystore's dual-encryption AES-GCM tag instead, and a mismatched file/keystore dual-encryption state now fails closed. Legacy files still decrypt unchanged; re-encrypt them to drop the weak verifier. Portable-USB integrity (2026-07-24, gitlab#132): integrity verification of a portable USB drive did not detect files added to the drive, including a root-level autorun payload auto-executed by the OS. New drives now record an allowlist of every file in the tool tree (plus the root autorun files) and flag ANY file added afterward — a planted library or any other payload, not just a fixed set of file types (the user's encrypt/decrypt workspace is excluded, so normal use still verifies); older drives verify as before, re-create a drive for the stronger checks. The hash-manifest fallback also now uses the drive's unique per-drive salt. Low security fixes (2026-07-24, gitlab#133–136): the plugin sandbox no longer authorizes a sibling plugin directory that shares a name prefix; the keyserver bearer token passed to keyserver set-token is now redacted in --debug output (rotate any token previously used with --debug); trust-anchor enrollment now requires the full key fingerprint instead of a forgeable short key id; and the PIV smartcard PIN is handled with one fewer non-wipeable in-memory copy. Desktop GUI — asymmetric decryption (gitlab#137): the Decrypt tab can now decrypt files encrypted to an identity. Its Advanced Options expose a decryption-identity selector (--with-key) and, once an identity is chosen, a verify-signature-from selector (--verify-from) and a skip-signature-verification checkbox (--no-verify); skipping verification is off by default and requires an explicit opt-in behind a clear warning. Desktop GUI — Password Generator (gitlab#139): a new Pro-mode screen generates passwords via the CLI in both character mode (length and character-class toggles) and diceware passphrase mode (word count, separator, optional custom wordlist), showing entropy/strength with copy-to-clipboard. Desktop GUI — Secure Shred (gitlab#140): a new Pro-mode screen securely overwrites and deletes files/directories via the CLI shred command with a selectable pass count and recursive toggle, gated behind a mandatory irreversible-action confirmation dialog. Desktop GUI — password-strength meter (gitlab#141): the Encrypt tab shows a live strength indicator (bar, category, entropy bits, weakness warnings) via the CLI check-password --json command, with the password passed on stdin and the check debounced. Desktop GUI — Rekey (gitlab#142): a new Pro-mode screen re-encrypts an existing file with a new password (and optionally a new algorithm) via the CLI rekey command, passing the old/new passwords through environment variables the CLI clears after reading. Recovery credentials via environment (2026-07-25, gitlab#144): a recovery code could previously be passed only with --recovery-code on the command line, where it is visible in the process list and — unlike --password — carried no warning, while recovery passphrases were reachable only through an interactive terminal prompt, so scripts and the desktop GUI could not use them safely or at all. OPENSSL_ENCRYPT_RECOVERY_CODE, OPENSSL_ENCRYPT_RECOVERY_PASSPHRASE and OPENSSL_ENCRYPT_ADD_RECOVERY_PASSPHRASE now carry these credentials for recover, add-recovery and remove-recovery; each is read once and deleted from the environment immediately — including when a command-line flag supersedes it — so it is not on the process list and is not inherited by a later child process, and passing a recovery code on the command line now warns. The primary file password supplied through CRYPT_PASSWORD is cleared the same way on these commands. An explicit flag still chooses which credential is used, so a stray or planted environment variable cannot silently add a recovery passphrase to a file, and a blank value is refused rather than leaving the tool waiting at a prompt. Note that clearing a variable does not scrub the copy visible in /proc/self/environ, so this protects the credential from other local users rather than from a compromised session of the user's own. Desktop GUI — Recovery Slots (gitlab#145): a new Pro-mode screen lists a file's recovery slots, adds a recovery code or passphrase, removes a slot behind an explicit confirmation, and decrypts a file with a recovery credential when the password is unavailable. A newly generated recovery code is shown once and never written to a log. The app also no longer records a command's standard output in its debug log by default, since that output can contain decrypted content or a newly generated credential. Recovery commands — machine-readable output (2026-07-25, gitlab#146): list-recovery, recover, add-recovery and remove-recovery gain a --json option, so scripts and the desktop app can read a file's recovery slots without parsing human-readable text, and the report now states which credential produced a newly added slot. A newly generated recovery code is never printed to the output or message streams in this mode — it unlocks the file, so the tool writes it to a file of your choosing that only you can read (--recovery-code-out), and the report contains just the path. Global options after a command (2026-07-25, gitlab#171): options such as --debug, --verbose and --quiet were rejected when written after a command name for roughly half the commands — including identity, keyserver, telemetry, plugin, test and the recovery commands — so the desktop app's debug toggle made every one of those commands fail before doing any work. They are now accepted after any command, and where a command declares its own --quiet the value is no longer silently discarded. Desktop GUI — contact import (2026-07-25, gitlab#164): importing a contact's public identity from the desktop app had never worked: the app sent options the command line did not accept, so every import failed immediately. identity import now reads the contact document from standard input (--data-stdin) and accepts a local --alias for the contact. The document is deliberately not accepted as a command-line value, because the command line is readable by every other process on the machine and the field it comes from is a free-text paste box — a mis-pasted private key would be exposed before the tool could reject it. An alias is a local label only: contacts are pinned by fingerprint, so an alias cannot disguise a changed key. Keyserver login redaction (2026-07-25, gitlab#171): the keyserver login identifier is a credential and is now redacted in --debug output and no longer written to logs, and third-party network libraries no longer log full request addresses under --debug (which could contain a contact's email address). Neither could occur in a released version, because --debug was previously rejected for those commands. Second password and signing passphrase via environment (2026-07-25, gitlab#154/#159): the second password for keyed hidden mode and the signing passphrase for sign could previously be entered only at an interactive terminal prompt, so scripts and the desktop app could not use those features at all. OPENSSL_ENCRYPT_SECOND_PASSWORD and OPENSSL_ENCRYPT_SIGNER_PASSPHRASE now supply them. Each is read once and cleared immediately so it is not passed on to other programs the tool starts, a blank value is refused rather than leaving the tool waiting at a prompt it cannot show, and neither variable can switch a feature on by itself — hidden mode still needs its option, and an identity protected only by hardware is never asked for a passphrase. Identity display sanitization (2026-08-07, gitlab#172): the email field of an imported contact document was printed to the terminal unchecked, directly above the fingerprint line used for out-of-band verification, so a malicious contact file could embed terminal control sequences that overwrite the displayed fingerprint with one the victim trusts. The same gap existed on the keyserver trust prompt — which displays a key bundle fetched from a remote server, an even stronger attack position — on stored identity files read back from disk, on several signature-file fields (including one printed inside the GOOD-signature verdict even though it is not covered by the signature), and in keyserver error messages that echoed a raw server response. Contact metadata (email, fingerprint, creation date) is now validated everywhere it enters the program (import, create, load from disk, keyserver bundle, signature sidecar), and every terminal display of it — including data imported or cached by earlier versions — escapes control characters instead of printing them, as do the error messages that echo a rejected name or alias. Desktop GUI — identity listing (2026-08-07, gitlab#183): the app's identity list was always empty: it asked the command line for machine-readable output using an option that did not exist, so every listing failed silently and the Identity Management screen, the Decrypt tab's identity selector and the main window all showed nothing. identity list --json now exists and the app lists identities again. Contact details displayed in the app additionally neutralize invisible text-direction characters, which could otherwise make an address render reversed. The app also reports store entries it could not load instead of leaving them out of the list silently, and an identity list that fails now shows an error instead of an empty list. Identity name collision (2026-08-07, gitlab#173): a contact could be stored under the same name as one of your own identities. The contact stayed hidden while your identity existed, but deleting that identity handed the name — and any file you later encrypted to it — to the contact's keys. Such a name is now refused outright, deleting a name removes both entries, and any collision already on disk is reported by identity list. Deleting such a name now asks which entry to remove and shows both fingerprints first, since removing your own identity destroys its private keys; the name contacts is also reserved, as an entry stored under it was hidden from the listing yet still usable. Envelope rewrite data loss (2026-08-07, gitlab#148): adding or removing a recovery slot, and rekeying a file, could rewrite it by truncating it — a crash, power loss or full disk part-way through left a shortened, unreadable file and no copy of the original, which is the very outcome recovery slots exist to prevent. The rewrite is now atomic: the new file is written alongside the original, flushed to disk, then renamed over it with its permissions preserved, so an interrupted write leaves the original untouched. Where a rename cannot be used — a symbolic link, or a file with more than one name (hard link), both of which have to be written through so every name stays consistent — the original is copied to a backup beside it first and put back if the write fails; if the restore fails too the backup is kept and its location is reported. Post-quantum keyfile (2026-08-08, gitlab#157): the --pqc-keyfile option could never save a key. The option that triggers saving was not accepted by the encrypt command at all, so pointing --pqc-keyfile at a new path was silently ignored — you got a one-off key, no file was written, and there was no way to open the encrypted file later with the keyfile you believed you had created. Saving now works, a missing keyfile is refused with a clear instruction instead of being ignored, and the key file is created readable only by you (previously it would have used the system default, typically readable by everyone on the machine). A second, older copy of this code that stored the post-quantum private key without any encryption has been removed. Seven documented commands could not be run (2026-08-08, gitlab#179): create-usb, verify-usb, list-plugins, plugin-info, enable-plugin, disable-plugin and reload-plugin were listed in the help output, documented, and backed by working code — yet every one of them stopped immediately with invalid choice, leaving the entire portable-USB and plugin-management command surface unreachable. Each was named in the list that decides which commands are handled by the newer command parser, but no such parser had ever been written for them, and nothing checked that those two things agreed. The program no longer keeps that list by hand: it reads which commands the newer parser actually handles, so a command it does not know now falls through to the parser that does. All 42 commands were verified to run. Pepper management commands (2026-08-09, gitlab#193): the remote-pepper server had working operations but no command-line access, so the desktop app's pepper controls failed silently. A new plugin pepper command group adds them — list stored peppers, test the connection, set up and verify TOTP two-factor authentication, and configure the pepper dead-man's switch. The two-factor secret and one-time backup codes are printed only to standard output (never to the log the app keeps) and are redacted from debug output. The dead-man's switch, which erases every pepper if you miss a check-in, now refuses an interval shorter than one day so it can never be armed with an already-past deadline; the destructive panic operation is deliberately not exposed. File-integrity verification commands (2026-08-09, gitlab#194): the remote file-integrity service likewise had no command-line access, so the app's integrity controls could not reach it. A new plugin integrity command group adds a connection test, verification statistics, and per-file verification. Verification deliberately reports four distinct outcomes — match, mismatch, file-not-registered, and service-unreachable — so a file the service has never seen, or a service that cannot be reached, is never mistaken for a tampered file (the mistake the removed app feature made); a malformed hash is reported as a usage error rather than as an unreachable service. OnlyKey identity wrong-device binding (2026-08-09, gitlab#218, security advisory 2026-18): creating an identity with identity create --hsm onlykey silently bound it to a YubiKey instead of the OnlyKey — the selected device was used only for an availability pre-check and never for the actual key protection, which always defaulted to the YubiKey. With only an OnlyKey attached, creation failed with a misleading “no Yubikey available” error; with both devices attached, the identity was gated by the YubiKey and could never be opened with the OnlyKey. The selected device is now threaded through identity creation and the private-key encrypt/decrypt paths, so an OnlyKey identity uses the OnlyKey end to end, and the error messages name the configured device. Existing YubiKey identities are unaffected. If you created an OnlyKey identity on an earlier release with both devices attached, re-create it on this release to bind it to the OnlyKey. Telemetry opt-out now sticks (2026-08-09, gitlab#166): opting out of the optional anonymous telemetry stopped uploads and deleted the stored key but wrote no persistent off-switch, so a telemetry-enabling environment variable that was still set silently turned collection back on and registered a fresh key the next time you ran the tool. Opting out now writes a persistent marker (~/.openssl_encrypt/telemetry/opted_out) that keeps telemetry off regardless of that environment variable until you remove the marker. Machine-readable security analysis (2026-08-09, gitlab#162): the analyze-security and smart-recommendations commands gain --output-format json, and telemetry status gains --json, each printing its result as JSON on stdout (the human report stays on stderr) so the desktop app reads the real security readout and telemetry state instead of guessing from human-readable text; the JSON carries only algorithm settings, scores and advice, never secrets. Credential-channel follow-ups (2026-08-09, gitlab#180): the signer passphrase environment variable is now cleared up front on the sign-while-encrypting path, before plugins and network connections start; the info command can now read a keyed hidden file's details non-interactively through the second-password environment variable (via --hidden-header) instead of only an interactive prompt; and the file-descriptor second-password input now applies the same blank-value rule as the other input methods. Secret-redaction hardening (2026-08-09, gitlab#147): several internal fixes so a secret can never surface through an encoding-error message, the debug log scrubber can no longer crash on an unusual value, a secret stays redacted in logs even after its environment variable is cleared, and passing a file password on the command line to the recovery commands now warns that it is visible in the process list. PIV / PKCS#11 identity protection (2026-08-10, gitlab#218): creating an identity protected by a PIV smartcard or PKCS#11 token now works end to end (identity create --hsm piv / piv-only). The token configuration is stored with the identity so it can be unlocked later without re-entering it, and none of the stored values is a secret. Existing Yubikey/OnlyKey identities are unaffected. Parallel key derivation for new files (2026-08-10, gitlab#220): the --parallel-kdf option did nothing for the file formats this version writes (v14 and v13), silently falling back to one-at-a-time key derivation. It now runs the independent key-derivation steps at the same time — across the number of workers set by --kdf-workers — while producing exactly the same key, so a file encrypted with --parallel-kdf still decrypts without it and vice versa. A required-but-unavailable RandomX step still stops the operation rather than weakening the key, and decrypting an untrusted file cannot use the option to exhaust memory. Legacy parallel-KDF path retired (2026-08-10, gitlab#224): older files (format v11/v12) used a separate implementation of --parallel-kdf that could silently skip a configured derivation step (Whirlpool) and could not handle another (Balloon) at all; those files now use the same single implementation as current files, so the option always honors the file's recorded configuration exactly, and an empty derivation configuration now produces a clear warning (or is refused when parallel derivation is requested) instead of silently producing a weak key. Parallel derivation limits (2026-08-10, gitlab#224): parallel key derivation now respects the number of processor cores and a memory safety limit — so encrypting with a very memory-hungry configuration cannot create a file that the memory-safety check later refuses to decrypt — and pressing Ctrl-C during derivation stops promptly instead of appearing to hang. Portable USB workspace now genuinely encrypted (2026-08-11, gitlab#263, security advisory 2026-43): the portable-USB creator advertised an “encrypted” AES-256-GCM workspace and set its config flags accordingly, but the workspace directory was left in cleartext — the encryption key was derived and then never used — so a user who trusted the label left files unencrypted on the removable drive. The workspace is now genuinely encrypted: the key seals it into a real authenticated AES-256-GCM vault (data/workspace.vault) created with the drive, and new crypt.py seal/unlock commands re-encrypt and open it, taking the master password from CRYPT_PASSWORD or a prompt (never the command line) and refusing a tampered oversized key-derivation config. The on-drive marker, README and config flags are corrected to say the truth: files left loose in the workspace are not encrypted until sealed, and removing unlocked files is an ordinary delete rather than a secure erase (which is not achievable on flash media). Re-create the portable drive to get the encrypted workspace. Recovery slots can no longer be stripped undetected (2026-08-12, gitlab#264, security advisory 2026-44): a file's recovery slots (extra ways to open it, such as a recovery code) could be deleted from the file header by anyone who could modify the file, and the owner's normal password decryption would silently succeed as if the slots had never existed. The number of recovery slots is now cryptographically bound to the wrapped key, so removing or altering them makes decryption fail closed instead of silently proceeding. Adding or removing a recovery slot now requires the primary password (a recovery code alone can no longer change the slots). Files made by older versions gain the protection once re-encrypted, or once a recovery slot is added or removed on this release.
1.4.8 STABLE RELEASE FEATURE SECURITY
2026-07-12
New check-password command reports password strength (pattern-aware category, entropy, weakness warnings, and pass/fail against a chosen policy) without encrypting anything, with --json for scripting. Pattern-aware password strength estimation now flags predictable structure (dictionary words, l33t substitutions, keyboard walks, sequences, repeats, dates) with an advisory-by-default label and an optional --strict-strength gate; encryption-time validation only, never decryption. The loud --debug data-logging banner now fires only for --debug --unsafe-show-secrets (the cleartext path), while plain --debug (which redacts secrets) shows a calm, accurate note. Security review follow-up (2026-07-07): removed an unconditional cleartext print of the derived FIDO2/HSM hardware pepper (H1); the plugin loader now verifies, hash-pins, AST-scans and executes the exact same bytes, closing a verify-one-copy/execute-another gap and a .pyc shadow (M1); package plugins are now covered by a signed per-package PLUGIN.manifest over every importable module, so a signed __init__.py plus a tampered sibling is refused under enforce (H2); no-op secure_memzero call sites that wiped a throwaway copy now wipe the real secret (M2); the parallel and sequential Independent-XOR paths derive identical keys for Argon2 multi-round configs (M3), RandomX fails closed in the parallel path (R1), and streaming per-chunk AEAD authentication failures are classified structurally (M4). Earlier hardening (audit 2026-07-06): per-round KDF debug lines no longer leak a derived-key intermediate by default, and new files are no longer written in the cost-bypassing v8/v10 sequential-XOR format (encrypt defaults to format version 9 and refuses new v8/v10; existing files still decrypt and rekey upgrades them). Also fixes string_entropy Unicode handling. Cross-line PQC KEM compatibility (2026-07-10): PQC KEM symmetric keys for format version 12+ files are now derived with HKDF-SHA256 (algorithm-name domain separation) matching the 1.5.x line, so v12 (streaming) and v13 (Independent-XOR) PQC files interoperate across the two maintenance lines; files written by releases up to 1.4.7 with the legacy bare-SHA256 derivation remain fully decryptable via an authenticated one-shot legacy retry that prints a re-encryption recommendation. Also fixes decryption of v11–v13 files carrying an embedded password-encrypted post-quantum private key (previously always failed with a missing-salt error). Format version 14 groundwork (not yet the default): new independent-XOR-only format with a length-prefixed KDF seed — password, salt and hardware pepper enter key derivation as unambiguous length-prefixed fields instead of raw concatenation (finding #100) — plus fail-closed version guards; v14 PQC files additionally bind the KEM symmetric key to the full transcript (algorithm, AEAD choice and encapsulation ciphertext, finding #83); all files below v14 derive byte-identically to before. Format version 14 is now the default write format: new encryptions (including streaming) default to the independent-XOR robust-combiner key derivation — as strong as the strongest KDF component instead of the sequential cascade's weakest link (finding M2) — wide keys (AES-SIV, Threefish) derive at full length (M1), sequential XOR stays available as a v13-pinned opt-in, and every existing file decrypts unchanged. Also fixes a data-loss bug where sequential XOR combined with streaming wrote files that could never be decrypted (now refused with a clear error), keystore dual-encryption failing for files at format versions 11–13, and a key-derivation crash when RandomX was combined with wide-key ciphers (AES-SIV, Threefish). Post-v14 review hardening (2026-07-11): the v14 KDF seed encoder now writes into a single exact-size buffer, so no partial copies of secret material can be left behind in unwiped reallocated memory (derived keys and the on-disk format are byte-identical); keystore metadata version checks now reject malformed version fields with a clean error instead of crashing on crafted files (valid files are unaffected); and recipient (asymmetric) files now bind the post-quantum key-encapsulation ciphertext and algorithm into the password-wrap key derivation (defense-in-depth transcript binding, wrap_version 3) — every existing file keeps decrypting, but recipient files written from this version on cannot be opened by older releases. Fully backward-compatible decryption. V14 follow-up hardening (2026-07-11): remote and combined KDF pepper material is now held in wipeable buffers and zeroized after use on the encrypt and decrypt paths (previously immutable copies could linger in memory until garbage collection; no derived keys or file formats change). Encrypting with an unknown future format_version is now refused up front instead of writing a permanently unreadable file. Legacy (pre-1.4.8) post-quantum files using XChaCha20-Poly1305 now decrypt via the intended legacy-key retry, and structural decode errors are no longer misreported as authentication failures. HSM test-command hardening (2026-07-12): the earlier H1 pepper-print fix had landed in a CLI frontend that is not actually dispatched — the live hsm fido2-test and onlykey-test handlers now report only the pepper length instead of hex-dumping the derived hardware pepper, the FIDO2 pepper plugin no longer includes raw prf/hmac-secret output in debug logs or error messages, and the module self-test prints lengths instead of test-secret hex; regression tests now cover the live code paths.
