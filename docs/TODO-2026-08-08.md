# Remaining work after the 2026-08-08 audit

Every open issue was checked against the code, not against the changelog —
that distinction mattered: the audit found two changelog entries describing
GUI controls that do not exist (gitlab#198), and it also corrected my own
first impression that gitlab#151 was unimplemented when it is simply built a
different way than the flag name suggested.

51 issues were open when the audit started; 19 were already implemented and
have been closed with evidence. These 32 remain, grouped by what they are
and ordered by what I would do first.

## Done since this file was written

- **#195** — same-file rewrites on the slow paths (1.4.x `0ac83af3`, 1.5.x
  `2502619d`). A review round caught that deriving only *identity* and then
  calling `os.replace` broke hard links, leaving one name readable under the
  retired password while reporting the rotation complete.
- **#149** — recovery passphrases now meet the password policy when a slot is
  created (1.4.x `aafae5af`, 1.5.x `8d337193`). Unlocking stays exempt, and
  1.5.x turned out to have had *no* check at all, so two Enter presses could
  wrap the file key under an empty passphrase.

- **#196/#197/#198** — landed earlier in this run (see the plan file).
- **#179** — the seven documented-but-unrunnable commands (1.4.x `35249ff7`,
  1.5.x `28f4358c`). The list that decided routing answered two questions at
  once; they are now separate, and the routing set is read off the built
  subparser so "routed but unregistered" is not representable.

  **The security review of that change found nine defects in the handler code
  it had just made reachable**, all now fixed and closed on both lines:

  | | | 1.4.x | 1.5.x |
  |---|---|---|---|
  | #199 | `enable/disable-plugin` reported success, persisted nothing | `e9184c21` | `8b8a36a3` |
  | #200 | `verify-usb` took its KDF cost from the untrusted drive (~29-day DoS) | `2a50950e` | `1d4fa557` |
  | #201 | every `secure_memzero` on the USB path was a no-op | `120f56f2` | `7001e28f` |
  | #202 | a planted FIFO hung `verify-usb` forever | `f0a30986` | `70338df6` |

  | #207 | root autorun files clobbered; drive secrets at the default umask | `2c0951ed` | `81ff3026` |

  None is a vulnerability in a released version — all nine live behind
  commands that exit 2 with `invalid choice` up to 1.4.8 — which is why they
  had to land in the same release as #179 rather than after it. Mirrored
  publicly as github#119.

  Found while porting, not fixed: **1.5.x's subparser registers
  `combine-secrets`, `split-secret` and `verify`, which nothing ever routes to
  it** — dead subparser definitions, the exact mirror of #179. All three work
  today via the monolithic parser, so the port used the *intersection* of the
  known-command list and the registry rather than the registry alone, to avoid
  a behaviour change outside the fix's scope. Worth its own issue.

- **#177 / #176** — argv-layer scanning (1.4.x `f7f7bc7a`, `94e086a3`;
  1.5.x `ae8f4f90`). `--` was ignored and an option *value* could be read as
  the command; `install-dependencies --yes` was rejected. Both scans are now
  one shared implementation reading the option sets off the real parser.

  The security review of that change found nine more, seven fixed inline
  (bundled `-qy` and abbreviated `--deb` swallowed the command; a leading
  `--` routed wrongly; the fallback set contradicted itself) and **one that
  affects released versions**:

  - **#209 / GHSA-jgvm-7jxv-cgcc / ADVISORY 2026-17** — the `--debug` argv
    dump printed the file password in cleartext for spellings argparse
    accepts but the sanitizer did not cover (`-apHunter2`, `-ap Hunter2`).
    Confirmed by running the **v1.4.8** sanitizer, not inferred. Fixed both
    lines; GHSA held until 1.4.9 ships, so the issue stays confidential.

  Also fixed there: `--keyring-remove` fired from a position argparse would
  not honour (`--identity-store --keyring-remove encrypt` deleted the entry
  named `encrypt`), was a silent no-op in two spellings, and reported a
  backend failure as success.

- **#174** — confirmation questions went to stdout while their warnings went
  to stderr (1.4.x `58415657`, 1.5.x `d5085780`). The issue named two sites;
  a lint found **21**, including the keyserver trust prompt, the telemetry
  opt-out and the KDF-cost override. The lint is now a test.
- **#156** — `--keyring-store` silently stored nothing when the password came
  from the environment (1.4.x `eace71a5`, 1.5.x `ca325096`). No error *and*
  no confirmation, so a user could discard their only copy of the password
  and lose the data. The store now runs on the resolved password.

- **#160** — `verify-signature --json` (1.4.x `7053b7d9`, 1.5.x `e4a9cadb`).
  Five refusal paths emitted no JSON at all, not the two filed; and the
  document exposed the unauthenticated component labels while withholding
  the authenticated `algorithm`.
- **#210** (new, found while testing #160) — `--identity-store` before the
  command was silently ignored (1.4.x `d25026b8`, 1.5.x `cd816e5e`). Third
  instance of the `--quiet`/`--yes` dest-clobber; on the destructive
  identity commands it meant operating on the *default* store while
  believing otherwise.

Deferred from #149, deliberately: a re-prompt loop when an interactive
passphrase fails the policy. Today the whole command aborts after the unlock
credential has already been consumed, which pushes the user toward
`--force-password`. It is a UX change around a credential prompt and deserves
its own issue rather than riding along.
